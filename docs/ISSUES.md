# Midnight でトークン化預金を実現する際の問題・課題メモ

デモ作成中に判明した問題・課題を時系列で記録する。
（凡例）**[環境]** 開発環境・ツール / **[設計]** 業務・アーキテクチャ設計 / **[技術]** Midnight の技術的制約 / **[運用]** 運用・UX

---

## 1. [環境] Compact コンパイラが Windows ネイティブ非対応

- Compact コンパイラ（`compact` CLI）は Linux / macOS のみ提供。Windows では WSL2 (Ubuntu) 上で動かす必要がある。
- Windows には同名の `compact.exe`（NTFS 圧縮ツール）が `C:\Windows\System32` に存在し、PATH 上で衝突する。誤って実行すると無関係な出力になるため注意。
- 銀行の開発端末は Windows + 制限付き環境が多く、WSL/Docker の利用許可が導入障壁になりうる。

## 2. [環境] Node.js バージョン要件が新しい

- midnight-js 4.x / 公式サンプルは Node.js `>=24.11` を要求（本端末の Windows 側は v12 で不可）。
- 本デモでは WSL 内に nvm で Node 24 を導入して対応。
- 社内標準 Node が古い組織では、ビルド環境の分離（WSL / コンテナ / CI）が必要。

## 3. [環境] ZK 証明に Proof Server が必要

- トランザクションごとに ZK 証明を生成する必要があり、Proof Server（`midnightntwrk/proof-server` Docker イメージ、既定 `http://localhost:6300`）を使う。
- Lace の設定で Proof Server の接続先を選択する。ローカル実行には Docker（本端末では Rancher Desktop）の起動が必要。
- 証明生成は数十秒〜分単位かかることがあり、即時決済のような UX を期待する預金業務では体感速度が課題。

## 4. [設計] プライバシーと「強制移転」の両立（トレードオフ）

- Midnight のネイティブ shielded トークン（Zswap コイン）は保有者の鍵でしか使えない。そのため発行体による **強制移転・強制償還・凍結** を実装できない。
- 本デモでは、コントラクトの公開レジャー上に `Map<口座ID, 残高>` を持つ **アカウント型（コントラクト管理型）トークン** を採用した。
  - 長所: 発行体が凍結・強制移転・強制償還を確実に実行できる。
  - 短所: **残高・送金額・送金先口座IDがチェーン上で公開** される（口座IDは秘密鍵のハッシュなので氏名とは直接結びつかないが、仮名性のみ）。
- 本番では以下のような検討が必要:
  - 残高をコミットメント（ハッシュ）化し、本人と発行体だけが平文を知る方式（発行体による強制操作は、規制当局鍵・発行体鍵による選択的開示と組み合わせる）
  - shielded トークン + 発行体の「償還・再発行」スキームで強制移転を代替する方式
  - 選択的開示（Selective Disclosure）による監督当局への開示フロー

## 5. [設計] 利用者の認証は「秘密鍵の知識の証明」

- 口座ID = `persistentHash("tdeposit:acct:" || secretKey)`。回路内で秘密鍵（witness）から口座IDを再計算し一致を証明することで、秘密鍵をチェーンに出さずに本人確認する。
- 課題:
  - 秘密鍵はブラウザのローカル（プライベートステート）に保存される。**端末紛失・ブラウザデータ削除で口座を操作できなくなる**。本番ではバックアップ／鍵ローテーション（発行体による口座ID付け替え＝強制移転で救済）手順が必要。
  - Lace ウォレットの鍵（手数料支払い用）と、コントラクト上の口座鍵が別物になる。利用者にとって「2 種類の鍵」がある点は UX 上分かりにくい。
  - デモでは 1 つのブラウザで複数の口座鍵（銀行・Alice・Bob）を切り替えて操作できるようにしている（手数料はすべて接続中の Lace ウォレットが支払う）。

## 6. [設計] 発行体鍵の単一障害点

- 発行体（銀行）権限はデプロイ時の秘密鍵 1 本に紐づく。漏えい・紛失時のリスクが大きい。
- 本番ではマルチシグ／閾値署名、権限分離（発行担当・コンプライアンス担当）、鍵の更新回路が必要。デモでは未実装。

## 7. [技術] 手数料（DUST）の扱い

- Midnight のトランザクション手数料は DUST（NIGHT 保有により生成）で支払う。Lace ウォレットに Preview 用の tNIGHT を Faucet から入手し、DUST の生成（指定）を行う必要がある。
- 預金者が手数料を意識しない UX にするには、銀行側が手数料を肩代わりする仕組み（スポンサード Tx 等）の検討が必要。

## 8. [環境] コンパイラ／ランタイム／レジャーのバージョン整合が厳格

- 最新の Compact コンパイラ（0.35.0）は `compact-runtime 0.20.0`（ledger v9 / onchain-runtime-v4、いずれも RC）向けのコードを生成する。
- 一方、安定版 midnight-js 4.1.1（公式サンプルが Preview で使用）は `compact-runtime 0.16.0`（ledger v8）を前提とする。
- 生成コードは `checkRuntimeVersion('0.x.y')` で実行時に厳密チェックするため、組み合わせを誤ると動かない。
- 本デモでは **コンパイラを 0.31.1 に固定**（`compact update 0.31.1`）して対応。Proof Server も ledger v8 系（`proof-server:8.0.3`）に揃える必要がある。
- 本番では、ネットワークのハードフォーク（ledger 更新）ごとに コンパイラ・SDK・Proof Server・ウォレットの更新と **コントラクトの再デプロイ／移行** が必要になる可能性があり、預金台帳の継続性の観点で大きな運用課題。

## 9. [技術] Compact の予約語・言語仕様

- `from` などが予約語で、構造体フィールド名や引数名に使えない（`sender` / `src` 等に変更）。
- 回路の引数やウィットネス由来の値を公開レジャーへ書き込む際は `disclose()` の明示が必須（書き忘れはコンパイルエラー）。プライバシー保護の観点では良い設計だが、「何を公開しているか」をレビューで必ず確認する必要がある。
- 符号なし整数の加減算は型が広がるため `as Uint<64>` のキャストが必要。オーバーフロー／アンダーフローは実行時チェックとなる（本デモでは事前に `assert` で残高不足を判定）。
- Midnight にはイベントログ機構がないため、操作履歴は **コントラクトの公開ステート（Map）に保存** した。ステート肥大化・手数料増加の要因となる（#12 も参照）。

## 10. [技術] ZK 証明鍵・WASM の配布サイズ

- 回路ごとに証明鍵（prover key）約 2.8MB が生成され、10 回路で約 28MB。加えて ledger WASM が約 10MB。
- ブラウザは初回操作時にこれらをダウンロードするため、モバイル回線や社内プロキシ環境では体感速度が悪化する。
- 機能（回路）を増やすほど鍵が増える。業務機能の追加＝回路追加＝コントラクト更新（検証鍵の差し替え）となる。

## 11. [技術] 公開ステートは誰でも列挙できる

- `Map` は Indexer 経由で誰でも全件取得できる。本デモの「口座一覧」も公開レジャーをそのまま表示している。
- つまり **全口座の残高・凍結状況・送金履歴が第三者から見える**。口座IDが仮名でも、取引パターンからの名寄せリスクがある。
- 預金の守秘義務を満たすには、残高のコミットメント化や shielded 化（#4）が必須。

## 12. [技術] 同時実行時の競合（スループット）

- Midnight のコントラクト呼び出しは、ローカルで回路を実行し「読み取った値」を含む公開トランスクリプトを証明する。送信までの間に同じ値が他のトランザクションで更新されると、そのトランザクションは失敗する。
- 本デモでは全操作が共通の `opCount`（履歴番号）を読むため、**同一コントラクトへの操作は実質的に直列化** される。同一口座の残高も同様。
- 多数の利用者が同時に送金する預金システムでは致命的になりうる。対策案: 履歴をオンチェーンに持たない（Indexer で Tx を追跡）、口座単位でステートを分割、バッチ処理、複数コントラクトへのシャーディング等。

## 13. [技術] 証明生成の委譲方式が API バージョンで変化

- DApp Connector API v4 では `getConfiguration().proverServerUri` が **非推奨** となり、`getProvingProvider()` でウォレットに証明生成を委譲する方式が推奨。
- 本デモは既定で `getProvingProvider()` を使い、失敗時は `proverServerUri`（または `http://localhost:6300`）へフォールバックする実装とした。
- ウォレットの実装・バージョン差異で挙動が変わりうるため、銀行が配布するアプリでは対応ウォレット・バージョンの固定と検証が必要。

## 14. [環境] フロントエンドのビルド周り

- Midnight SDK は WASM・トップレベル await・Node 由来モジュール（`Buffer`, `process`, `assert`, `isomorphic-ws`）を含み、ブラウザ向けバンドル設定が必要（公式サンプルの Vite 設定を流用）。
- Vite 8 では `vite-plugin-top-level-await` が esbuild/rollup を要求して動かないため除外した（`target: esnext` でネイティブ TLA を使用）。
- `isomorphic-ws` の `WebSocket` が undefined になる警告が出るため、Indexer プロバイダに `window.WebSocket` を明示的に渡した。

## 15. [環境] 社内ネットワークでの TLS 証明書失効確認

- 本端末の Windows `curl`（schannel）では Preview Indexer への接続が `CRYPT_E_NO_REVOCATION_CHECK` で失敗した（`--ssl-no-revoke` で接続可能、ブロック高 約 156 万を確認）。
- 証明書失効確認（OCSP/CRL）が遮断されたプロキシ環境では、ツールやウォレットが Midnight の各エンドポイント（Indexer / Node / Faucet）に接続できない可能性がある。銀行内での検証時はネットワーク部門との調整が必要。

## 16. [設計] 償還時の法定通貨払戻しとの連携

- `redeem` はトークンを消却するだけで、預金口座への払戻し（法定通貨側）はオフチェーン処理となる。
- 本番では、勘定系システムが Indexer で償還トランザクションを検知し、口座ID→顧客口座のマッピングで入金する仕組み、二重払い防止（冪等性）、日次の **オンチェーン発行残高と勘定系残高の照合** が必要。
- 発行（入金→`issue`）も同様に、勘定系での入金確認とのアトミック性は保証されない。

## 17. [設計] 金額表現

- 残高は `Uint<64>`（小数なし）で、円の 1 円単位を想定。外貨や小数点以下を扱う場合は桁（decimals）の設計が必要。
- `Uint<64>` 上限（約 1.8×10^19）は円建て預金では十分だが、合計値計算時のオーバーフローチェックは回路内で行われる（失敗時はトランザクション拒否）。

## 18. [運用] テストの自動化

- 業務ロジックは `compact-runtime` のローカルシミュレータで自動テスト可能（`test/tdeposit.test.ts`、9 ケース）。証明生成・ネットワークなしで高速に回せる。
- 一方、Lace ウォレットを介した E2E（承認ポップアップ、DUST 支払い、証明生成、ブロック取り込み）は自動化が難しく、手動確認が中心になる。
- 本デモ作成時点では、Lace 経由の Preview 上での実行は利用者側で確認する必要がある（開発端末から Lace を操作できないため）。

## 19. [運用] DUST（手数料）入手の手順が分かりにくい

- Faucet で tNIGHT を受け取っただけでは DUST は生まれない。Lace の **Tokens → 「Generate tDUST」**（NIGHT の UTXO を DUST 生成に登録する Tx）を別途実行する必要がある。
- 登録後も DUST は **時間経過で少しずつ蓄積** されるため、すぐには手数料を払えない（数分〜数十分待つ）。
- Lace の Proof Server を Local に設定している場合、Proof Server（Docker）が起動していないと DUST 生成 Tx 自体が進まない可能性がある。手順の順序（Docker 起動 → Proof Server → Generate tDUST → デプロイ）を誤るとつまずく。
- デモ準備でも実際につまずいた点であり、一般の預金者に「NIGHT を保有して DUST を生成し手数料を払う」操作を求めるのは現実的でない。銀行による手数料肩代わり（#7）、もしくは銀行側で DUST を用意したうえで Tx を中継する設計が必要。

## 20. [環境] 社内 TLS 検査（Netskope）で Proof Server が起動しない

- 症状: `proof-server` コンテナが起動直後に終了。ログに
  `Failed to fetch data from https://midnight-s3-fileshare-dev-eu-west-1.s3.eu-west-1.amazonaws.com/bls_midnight_2p10 after 3 attempts`。
- 原因: Proof Server は起動時に **公開パラメータ・Zswap/DUST 用の証明鍵を Amazon S3 からダウンロード** する。社内ネットワークでは Netskope が HTTPS を中継し独自証明書（`ca.netskope-cac.goskope.com` ← `certadmin` ルート）で再署名しているため、Netskope ルート証明書を持たないコンテナが TLS 検証に失敗する（WSL Ubuntu からは正常に取得できた）。
- 対処（本デモで実施）:
  1. Windows の証明書ストアから Netskope 関連のルート証明書を PEM で書き出し → `certs/netskope.pem`
  2. Ubuntu の CA バンドルと結合 → `certs/ca-bundle.crt`
  3. `proof-server.yml` でコンテナの `/etc/ssl/certs/ca-certificates.crt` にマウントし、`SSL_CERT_FILE` を設定
  4. ダウンロード済みパラメータは名前付きボリューム（`proof-params`）に保存し、再起動時の再取得を回避
- 他にも直前の注意点として、Rancher Desktop は Kubernetes 有効時に起動完了まで数分かかり、その間は `docker` コマンドが `//./pipe/docker_engine` エラーになる。
- 示唆: 銀行の閉域・TLS 検査環境では、Proof Server が外部（S3）に依存すること自体がリスク。本番ではパラメータを事前取得して内部配置する、もしくは許可リストへの登録が必要。

## 21. [運用] Lace の UI がバージョンで大きく異なり、公式手順と一致しない

- 公式サンプル（Lace 1.36.0 で検証）の手順「Tokens → Generate tDUST」が、利用した新しい Lace（マルチチェーンの「ポートフォリオ」画面、日本語 UI）では **トークン一覧・tNIGHT 詳細のどちらにも見当たらなかった**。
- 新しい Lace では証明生成の選択肢も変わっている:「このアプリで実行（WASM）」（ブラウザ内で証明生成）／「カスタムプルーフサーバー」（例: `http://localhost:6300`）。
  - WASM を選べば Docker 不要になる可能性がある一方、メモリ不足でウォレットが落ちる可能性が画面上で警告されている。
- ウォレットの UI・手順がドキュメントより先に変わるため、利用者向けマニュアルの維持が難しい。銀行が顧客に配布する場合は、対応するウォレットとバージョンの固定、あるいは自社アプリへのウォレット機能組込みを検討する必要がある。

## 22. [技術] Lace の接続先が Blockfrost（サードパーティ）になっている

- Lace の Midnight 設定では、ノードとインデクサーが `rpc.midnight-preview.blockfrost.io` / `midnight-preview.blockfrost.io/api/v0`（project_id 付き）になっていた。
- DApp は `getConfiguration()` でウォレットの接続先を受け取って使うため、**Midnight 公式インデクサーではなく Blockfrost 経由で状態を参照する** ことになる。互換性（GraphQL・WebSocket 購読）の確認が必要。
- 銀行システムとしては、第三者インフラへの依存、可用性（SLA）、照会内容がプロバイダから見えること、を評価する必要がある。自前のノードとインデクサーを運用する選択肢も検討対象。

## 23. [技術] DUST の代替生成ツールと、ウォレット同期の遅さ・不安定さ

- Lace の UI から DUST を生成できなかったため、`tools/dust/designate.ts` を作成した。
  - デモ専用ウォレットを作成し、Faucet から tNIGHT を **API 経由で自動取得**（`midnight-tmnight-preview.nethermind.dev`）する。
  - その NIGHT UTXO を DUST 生成に登録し、**DUST の受取先を Lace の DUST アドレスに指定** する（`registerNightUtxosForDustGeneration(..., dustReceiverAddress)`）。
  - Lace のリカバリーフレーズは不要。NIGHT の保有者と DUST の利用者を分けられるという Midnight の仕組み（designation）を活用している。
  - 示唆: 銀行が NIGHT を保有し、顧客（またはDApp 中継者）の DUST アドレスへ DUST を供給する「手数料スポンサー」モデルが、この仕組みで実現できる可能性がある（#7, #19）。
- 課題:
  - 新規ウォレットの **初回同期に約 13 分** かかった（Preview 約 156 万ブロック、WSL 上の Node）。同期状態を保存しないと、毎回この時間がかかる。
  - Faucet が `OK` を返した後、着金待ちの間に `Wallet.Sync: ErrorEvent`（WebSocket エラー）が発生し、同期が止まったまま着金を検知できなくなった（25 分以上）。再起動が必要だった。
  - **Faucet API は `OK` を返したのに、2 回とも tNIGHT が届かなかった**（1 時間以上待っても残高 0）。ブラウザの Faucet 画面から手動で請求すると約 3 分で着金した。自動化の前提にできない。
  - 結果: 登録 Tx `00f5b4c26073944ddfe345b3cfef42ef80fb3029875b6b423c22b2c4e4f8331dbf` を送信（手数料見積り 1001、ZK 証明生成は約 20 秒）。受取先は Lace の DUST アドレス。
  - Indexer v4 の GraphQL には、アドレスの残高を直接照会するクエリがない（購読のみ）。障害時の切り分けがしにくい。
  - 銀行システムとして顧客の資金状況を監視する場合は、独自のインデックス（または安定した同期基盤）が必要になる。

## 24. [運用] 単一 HTML での配布は可能だが重い

- JS / WASM（ledger 約 10MB + onchain-runtime 2 本）/ ZK 証明鍵（10 回路で約 27MB）をすべて base64 で埋め込むと、**HTML 1 枚で約 55MB** になる。
- 初回の表示（55MB の解析と WASM のコンパイル）に十数秒かかる。メール添付やチャット共有には向かない。
- `file://` で開く場合は、Lace 拡張の「ファイルの URL へのアクセスを許可する」を ON にしないとウォレットが注入されない。社内ポリシーで拡張の設定変更が禁止されている環境では、ローカル HTTP 配信（`start-single.cmd`）が必要。
- 開いた URL（オリジン）ごとに localStorage が分かれるため、口座鍵（特に発行体の鍵）が配布形態によって引き継がれない。本番では鍵の保管場所をブラウザに依存させない設計が必要（#5）。
