# Midnight でトークン化預金を実現する際の課題

銀行が Midnight 上で**トークン化預金**（預金を裏付けとするトークンの発行・移転・償還と、凍結・強制移転などの統制）を実現しようとするときに生じる課題を、重要度別に整理したものです。

| 項目 | 内容 |
|---|---|
| 根拠 | Midnight Preview（テストネット）で、発行・移転・償還・強制移転・強制償還・凍結・全体停止を行うコントラクトを実装・検証した結果（2026-11-02〜11-10）。個々の事象は [ISSUES.md](ISSUES.md)（時系列の記録）の番号で参照する |
| 対象 | Midnight の仕様・技術的制約・エコシステムに起因し、トークン化預金の業務・規制・運用に影響する課題 |
| 対象外 | 検証用デモの実装・画面・配布方法だけに関わる問題（[ISSUES.md](ISSUES.md) に記録）、開発環境の構築手順（[SETUP.md](SETUP.md) に反映） |
| 前提 | 検証で使ったコントラクトは、凍結・強制移転を確実に行うため、**残高を公開台帳（コントラクトの公開ステート）で管理する方式**を採った。方式を変えると、一部の課題の性質が変わる（C1 を参照） |

**重要度の基準**

| 重要度 | 基準 |
|---|---|
| **C**（クリティカル） | 解決しないと、預金業務として成立しない・法令やリスク管理上の要件を満たせない |
| **M**（ミディアム） | 本番化までに対策が必要。業務は成立するが、品質・コスト・運用負荷に大きく影響する |
| **L**（ロウ） | 設計・運用で吸収できる。開発効率や利便性の問題 |

## 2. 課題一覧

| ID | 重要度 | 区分 | 課題 | 内容（何が問題か） | 影響 | 対応の方向性 | 根拠（ISSUES.md） |
|---|---|---|---|---|---|---|---|
| C1 | **C** | 設計 / 規制 | プライバシーと強制措置（強制移転・凍結・強制償還）の両立 | Midnight のネイティブの shielded トークンは、保有者の鍵がないと動かせず、発行体が強制措置をとれない。強制措置を確実に行うために残高を公開台帳で管理すると、**全口座の残高・送金額・送金先を誰でも参照できる**。口座IDは仮名でも、取引パターンから名寄せされるおそれがある。アプリの画面で他人の情報を隠しても、台帳を直接読めば分かるため、守秘にはならない | 預金の守秘義務を満たせない。または、規制上必要な凍結・差押え・誤送金の訂正ができない | **秘匿ノート方式**（残高をコミットメントのノートとして Merkle 木に置き、KYC・凍結は秘匿の所属証明、強制措置は発行体専用の回路、ノートの中身は銀行宛てに暗号化して公開）で、要件を満たせる見込み。シミュレータで動作を確認済み（[C1_PRIVACY_STUDY.md](C1_PRIVACY_STUDY.md)）。ネイティブの shielded トークンは凍結・差押えができないため単体では不可。回路が 2〜4 倍になる（M4）。実ネットワークでの検証と、公開されるメタデータの範囲について法務・コンプライアンスとの合意が必要 | #4, #11, #27, #39 |
| C2 | **C** | 技術 / 性能 | 同時実行の競合によるスループットの制約 | トランザクションは、ローカルで読み取った値を前提に証明を作る。送信までに同じ値が更新されると失敗する。共通のカウンタ（履歴番号など）や同じ口座の残高を更新する操作は、**同一コントラクトに対して実質的に一件ずつしか通らない**。複数口座の一括登録・一括発行のような処理も、専用の回路がなければ件数分のトランザクションを順に送ることになる | 多数の預金者が同時に送金すると失敗・再試行が多発し、大量の決済をさばけない | オンチェーンの共有カウンタや履歴を持たない設計。口座単位でのステートの分割。複数コントラクトへのシャーディング。一括処理用の回路や、1 つのトランザクションに複数の呼び出しをまとめる仕組み（midnight-js 5.0.0 の scoped transaction）の活用。目標スループットでの負荷検証 | #12, #29 |
| C3 | **C** | 設計 / リスク管理 | 発行体鍵・利用者鍵の管理と権限分離 | 発行体の権限は秘密鍵 1 本に結びつく（単一障害点）。発行・凍結・強制移転などの統制操作は、**発行体の鍵 1 本で単独に実行できる**。起票 → 承認の業務フロー（maker-checker）は、コントラクトで強制しない限りアプリ側の取り決めにすぎない。利用者の口座鍵を端末（ブラウザなど）に保存すると、端末の紛失やデータの削除で口座を操作できなくなる。口座鍵と手数料用のウォレット鍵の 2 種類があり、利用者に分かりにくい | 鍵の漏えいで不正な発行・強制移転が起きる。鍵の紛失で預金を動かせなくなる。権限分離を監査で示せない | マルチシグ / 閾値署名と権限分離（発行担当・コンプライアンス担当）。申請 ID と承認者の証明を回路の入力にする。鍵の更新回路。HSM・KMS・カストディの採用と、サーバー側での証明の生成。紛失時の救済手順（本人確認 → 強制移転で新しい口座IDへ付け替え）。ウォレットの鍵と口座鍵の統合 | #5, #6, #24, #25, #30 |
| C4 | **C** | 技術 / 運用 | ネットワーク更新に伴う互換性の破壊と台帳の継続性 | コンパイラ・ランタイム・ledger・SDK・Proof Server・ウォレットの**バージョンが厳密に結びついている**。ledger の更新（2026-11 の ledger 8 → 9）では、SDK のメジャー更新、コードの改修（状態の取得・プライベートステート・プロバイダ）、コントラクトの再コンパイル、証明鍵の作り直しが必要になった。検証では、動いていた構成が**約 1 週間で使えなくなった**。テストネット（Preview）は新しいチェーンとして作り直され、資金（tNIGHT・DUST）とコントラクトがすべて失われた。ウォレットはリセット前の残高を表示し続け、DApp からも資金があるように見えた | 預金台帳（残高・履歴）の継続性が保てない。移行時の停止や不整合のリスク。追随のための改修コストが継続的に発生する | バージョン管理と更新計画を Midnight のロードマップと連動させる。更新の予告と移行期間を前提にした運用体制。コントラクトに移行用の回路（残高のスナップショット・移管）を用意する。ステージング環境での事前検証。テストネットのリセットを前提にした検証手順（状態の確認、資金の再取得） | #8, #35, #37, #38 |
| C5 | **C** | 業務 | 勘定系（法定通貨）との整合 | 発行（入金 → mint）と償還（burn → 払戻し）のどちらも、オンチェーンとオフチェーンの処理がアトミックではない。入金では預金のロックからトークンの発行まで、償還ではトークンの消却から預金への入金まで、**途中の状態が必ず生じる**。発行残高と勘定系の残高の照合は、単純な一致判定ではなく、処理待ちを差し引いた「説明できない差異」で判定する必要がある | 二重払い、払戻し漏れ、オンチェーンの発行残高と勘定系の残高の不一致 | 勘定系による償還トランザクションの検知（Indexer の購読）。申込 ID をオンチェーンの記録に含め、勘定系の処理と 1 対 1 で突き合わせる。口座IDと顧客口座の対応付け。冪等な払戻し処理。処理待ちを考慮した日次照合。例外時の訂正手順（強制移転・強制償還） | #16, #26 |
| M1 | **M** | 設計 / UX | 手数料（NIGHT / DUST）モデル | 手数料は DUST で払う。DUST は NIGHT を「DUST 生成」に登録し、**時間とともにたまる**もので、受け取っただけでは増えない。預金者に NIGHT の保有と DUST の管理を求めるのは現実的ではない。一方で、手数料を払う主体（DUST の保有者）と、操作の権限を証明する主体（口座の鍵）は分けられ、DUST の生成先を別のアドレスに指定することもできる | 預金者が操作できない。手数料コストが読めない | 銀行が NIGHT を保有し、手数料を肩代わりする「手数料スポンサー」モデル（DUST の生成先の指定、または銀行のバックエンドからのトランザクション送信）。DUST の必要量の見積りと補充の運用 | #7, #19, #23, #30 |
| M2 | **M** | 技術 / 運用 | ウォレットへの依存 | ウォレット（Lace など）の画面・手順・API がバージョンで大きく変わる（公式手順の「Generate tDUST」が見当たらない、証明の委譲方式の変更など）。ウォレットの接続先（ノード・Indexer）や証明サーバーの設定は**利用者も DApp も確認・変更できない**ことがあり、端末ごとの設定の違いやウォレット側の障害が、そのまま業務の障害になる。検証では、ネットワークの更新後に特定のウォレット（Lace）が使えなくなり、別のウォレット（1AM）に切り替えた。ウォレットが組み込まれる条件（`file://` では組み込まれない、サイトへのアクセス設定など）にも左右される | 利用者向けマニュアルを維持できない。ウォレットの更新や障害で突然動かなくなる | 対応するウォレットとバージョンの固定と検証。複数ウォレットへの対応（DApp Connector API の共通部分だけを使う）。銀行アプリへのウォレット機能の組み込み（ウォレット SDK の利用）。接続先を銀行が管理できる構成 | #13, #21, #33, #34, #36 |
| M3 | **M** | 技術 / リスク管理 | 外部インフラへの依存 | ウォレットの接続先が第三者のインフラ（Blockfrost）で、ネットワークの更新に追従せず、古いチェーンのまま止まってエラーを返した。Mainnet・Preprod の Midnight 運営の接続先は廃止され、第三者（Blockfrost、トークン必須）に移っている。Proof Server は起動時に外部（S3）からパラメータを取得する。Faucet の API は「OK」を返しても送金されないことがあった。依存先が止まると、ウォレットは原因の分からないエラー（`Internal Server Error`、メッセージなし）を返す | 第三者の可用性・SLA に業務が左右される。照会内容が事業者から見える。障害の切り分けに時間がかかる | 自前のノード・Indexer・Proof Server の運用。パラメータを事前に取得して内部に配置。外部依存先の SLA 評価と代替経路。操作前の依存先のヘルスチェック。ウォレットのエラーを業務向けの文言に変換する仕組み | #20, #22, #23, #34, #36 |
| M4 | **M** | 技術 / UX | 証明生成の性能と配布サイズ | 操作ごとに「回路の実行 → ZK 証明 → ウォレットの承認 → 送信 → ブロックへの取り込み」が必要で、1 件に数十秒〜数分かかる。証明鍵は大きく、ledger 9 では 1 回路約 11MB（10 回路で約 108MB。ledger 8 の約 4 倍）、ledger の WASM も数十 MB ある | 即時決済の UX にならない。モバイルや低速回線で使いにくい。配布物が大きく、初回の読み込みが重い | 回路の最適化と統合。証明の性能確保（サーバー側での証明、ハードウェアの選定）。鍵のキャッシュや遅延読み込み。非同期の完了通知と進捗表示を前提にした業務・画面の設計 | #3, #10, #24, #29, #38 |
| M5 | **M** | 技術 / 運用 | コントラクトの機能追加と移行 | 業務機能を追加すると回路が増え、検証鍵の差し替えか再デプロイが必要になる。ledger の更新で再コンパイルすると検証鍵が変わり、更新前にデプロイしたコントラクトとの対応にも注意が要る | 制度変更や機能追加・ネットワークの更新のたびに、移行作業が発生する | コントラクトの保守権限（maintenance authority）による検証鍵の更新手順の確立。移行回路の設計。回路を小さく分ける設計 | #10, #38 |
| M6 | **M** | 技術 / 運用 | 監視・照会・監査の仕組み | Midnight にはイベントログがなく、履歴をコントラクトのステートに持つとステートの肥大化と手数料増の要因になる。ステートに持つ履歴には日時・Tx ハッシュがなく、監査証跡として使うには別の記録と突き合わせる必要がある。Indexer にはアドレスの残高を直接照会するクエリがない。ウォレットの同期は初回で十数分かかり、通信エラーで止まることがあった | 取引監視（AML）、監査証跡、障害時の切り分けが難しい | 独自のインデックス（Indexer の購読 → 自社 DB に Tx と状態の変化を記録）。オンチェーンの履歴は最小限にする。監視用の安定した同期基盤（状態の永続化と自動再接続） | #9, #23, #28 |
| M7 | **M** | 運用 | 銀行の閉域・TLS 検査環境との相性 | 社内の TLS 検査（Netskope など）で、コンテナが証明書の検証に失敗し、Proof Server が起動しなかった。Windows の curl も証明書の失効確認で失敗した | 行内の環境で検証・運用ができない。ネットワーク部門との調整に時間がかかる | 社内 CA の配布手順の標準化。必要な通信先の許可リスト化。外部通信が不要な構成（パラメータの内部配置、M3） | #15, #20 |
| M8 | **M** | 設計 / 業務 | DvP（資産トークンとの同時決済）の実現性 | トークン化預金を証券などの決済に使う場合、資金と資産の引き渡しを 1 つのトランザクションで行う DvP が必要になる。複数のコントラクトにまたがる呼び出しのアトミック性、または同一コントラクト内での資金と資産の管理が必要で、**検証では未確認** | 資金と資産の片方だけが動くリスク。証券決済などの主要なユースケースに使えない | 資産トークンを含むコントラクトの試作と、アトミック性の検証。C1（プライバシーの方式）・C2（同時実行）と合わせて方式を選ぶ | #32 |
| L1 | **L** | 設計 | 金額表現 | 残高は `Uint<64>`（小数なし、1 円単位を想定）。外貨や小数点以下は扱えない | 多通貨・利息計算への対応 | 通貨ごとの桁数（decimals）の設計。オーバーフローを考慮した型の選択 | #17 |
| L2 | **L** | 技術 / 品質 | Compact の言語仕様・公開範囲・エラー設計 | 予約語（`from` など）、整数演算のキャストなど、独自の仕様がある。公開台帳に書き込む値は `disclose()` の明示が必須（プライバシー上は良い設計）で、何を公開しているかのレビューが欠かせない。業務上の拒否（凍結中・残高不足など）は `assert` のメッセージ文字列でしか返らない | 開発の習熟コスト。公開範囲の誤り。アプリ側でのエラーの判別が文字列頼みになる | コーディング規約と、`disclose` を対象にしたレビュー観点の整備。エラーコードの体系化。シミュレータテストの活用 | #9, #31 |
| L3 | **L** | 品質 | E2E テストの自動化 | 業務ロジックはローカルのシミュレータで自動テストできる。一方、ウォレットの承認・DUST の支払い・証明・ブロックへの取り込みを含む E2E は自動化が難しい | 回帰テストの工数 | ウォレット SDK を使ったヘッドレスの E2E。テスト専用ネットワーク（ローカルのネットワークなど）の利用 | #18 |
| L4 | **L** | 環境 | 開発環境の制約 | Compact コンパイラは Linux / macOS のみ（Windows では WSL が必要）。Node.js 22.12 以上が必要。Proof Server に Docker が必要 | Windows 中心の開発部門での導入障壁 | WSL / コンテナ / CI でのビルド環境の標準化（SETUP.md） | #1, #2, #3 |

## 3. 検証で確認できた Midnight の特長

課題の裏返しとして、トークン化預金に有効と確認できた点です。方式の検討の材料にしてください。

| 特長 | 内容 | 関連 |
|---|---|---|
| 鍵を公開しない権限・所有の証明 | 発行体であること・口座の保有者であることを、秘密鍵を公開せずにゼロ知識証明できる。チェーンに記録されるのは口座ID（鍵のハッシュ）だけ | C3 |
| 統制のルールをコントラクト自身が判定 | 凍結中・全体停止中の操作は、証明を作る前の回路の実行で拒否され、トランザクションは作られない（手数料もかからない）。銀行のシステムを経由しなくても統制が効く | C1, L2 |
| 公開範囲の明示 | 公開台帳に書く値は `disclose()` の明示が必要で、何を公開しているかをコードで確認できる | C1, L2 |
| 手数料を払う主体と権限の主体の分離 | DUST の保有者（手数料）と口座の鍵（権限）を分けられ、DUST の生成先も指定できる。銀行による手数料の肩代わりの土台になる | M1 |
| ウォレットに依存しない接続 | DApp Connector API は共通で、同じ DApp を複数のウォレット（1AM・Lace）で動かせる | M2 |

## 4. 優先して検討すべき事項

1. **C1（プライバシーと強制措置）の方式決定**
   アーキテクチャ全体を左右します。法務・コンプライアンスと「誰に何をどこまで見せてよいか」を合意し、方式を選んでください。秘匿ノート方式で両立できる見込みを PoC で確認済みです（[C1_PRIVACY_STUDY.md](C1_PRIVACY_STUDY.md)）。次は実ネットワークでの性能の確認です。
2. **C2（スループット）の早期検証**
   C1 の方式によってステートの持ち方が変わるため、方式の候補ごとに、目標件数での負荷試験をしておく必要があります。
3. **C3・C5（鍵管理・権限分離と勘定系連携）**
   既存の銀行システム（HSM、勘定系、照合）と組み合わせる前提で設計してください。統制操作の権限分離は、コントラクトで強制する方式を検討してください。
4. **C4（バージョン追随）と M2・M3（ウォレット・外部依存）**
   ネットワークの更新は短い間隔で起こりえます（検証期間中にも ledger の更新とテストネットの作り直しがあった）。Midnight 側のロードマップを確認し、更新計画、自前インフラ、利用するウォレットの方針を決めてください。
5. **M8（DvP）の実現性の確認**
   証券決済などに使う場合は、資金と資産の同時決済ができるかを早めに試作で確認してください。
