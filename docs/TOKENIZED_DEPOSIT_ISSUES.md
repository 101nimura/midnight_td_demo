# Midnight でトークン化預金を実現する際の課題（重要度別）

デモ作成中に記録した課題（[ISSUES.md](ISSUES.md)）から、**Midnight 上でトークン化預金を実現する際に生じる課題**に絞って、重要度別に整理したものです。

- 2026-11-10 追記: Pactora UI 版（`dist-pactora/pactora-tdeposit-demo.html`。画面のベースは `pactora-phase2-usecase-mock.html`）の作成で出た課題（ISSUES.md #25〜#32）を反映しました。既存の課題への追記は「（Pactora UI 版）」と記載しています。新規は M8 です。

- 対象外としたもの: このデモの開発環境だけの問題（Git Bash のパス変換、開発サーバーのポート競合・ファイル監視、Windows の `compact.exe` との名前の衝突など）。これらは [SETUP.md](SETUP.md) の手順に反映しています。
- 重要度の基準

| 重要度 | 基準 |
|---|---|
| **C**（クリティカル） | 解決しないと、預金業務として成立しない・法令やリスク管理上の要件を満たせない |
| **M**（ミディアム） | 本番化までに対策が必要。業務は成立するが、品質・コスト・運用負荷に大きく影響する |
| **L**（ロウ） | 設計・運用で吸収できる。開発効率や利便性の問題 |

## 3. 優先して検討すべき事項

1. **C1（プライバシーと強制措置）の方式決定**
   アーキテクチャ全体を左右します。法務・コンプライアンスと「何をどこまで公開してよいか」を合意し、方式（公開台帳 / コミットメント + 選択的開示 / shielded + 再発行）を選んでください。
2. **C2（スループット）の早期検証**
   C1 の方式によってステートの持ち方が変わるため、方式の候補ごとに、目標件数での負荷試験をしておく必要があります。
3. **C3・C5（鍵管理と勘定系連携）**
   既存の銀行システム（HSM、勘定系、照合）と組み合わせる前提で設計してください。
4. **C4（バージョン追随）と M3（外部依存）**
   Midnight 側のロードマップを確認し、運用体制（更新計画、自前インフラ）を決めてください。
