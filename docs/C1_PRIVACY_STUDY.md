# 調査: C1「プライバシーと強制措置の両立」を Midnight の機能で解消できるか

[TOKENIZED_DEPOSIT_ISSUES.md](TOKENIZED_DEPOSIT_ISSUES.md) の **C1** について、Midnight の機能で解消できるかを調べた結果です（2026-11-10、Compact 0.36.0 / compact-runtime 0.21.0 / ledger 9）。

2026-11-12 に、7 章のステップ 1（銀行宛て・受取人宛ての暗号化を送金・発行の回路に組み込む、口座の葉をコミットメントにする）を PoC に実装し、5 章・6 章を更新しました。

## 1. 結論

- **Midnight の機能を組み合わせれば、C1 は原理的に解消できる見込みが高い。** 「残高・金額・送金元・送金先は一般には見えない」と「銀行は凍結・強制移転・強制償還ができ、全取引を把握できる」を両立する方式（本書の方式 C）を設計し、検証用のコントラクトで動作を確認した（シミュレータ）。
- ただし、**そのまま使える既製の機能はない**。
  - Midnight のネイティブの shielded トークンは秘匿性が高いが、発行体が凍結・差押えする仕組みはない
  - 方式 C は、コミットメント・Merkle 木・ナリファイア・楕円曲線暗号という部品を、コントラクトとして自前で組み上げる必要がある
- 代わりに次のコストがかかる。
  - 証明の回路が大きくなる（M4）。暗号化を組み込んだ送金・強制移転の証明鍵は約 99MB で、現行（約 11MB）の約 9 倍
  - ノートの受け渡しは、受取人宛ての暗号化で解決できた（オフチェーンでの共有は不要）。ただし受取人は、全ノートの暗号文を試しに復号して自分宛てを探す必要がある
  - メタデータ（どの操作をいつ行ったか）は公開されたまま残る
- 実ネットワークでの動作、証明時間、同時実行の性能は**未検証**。次の段階の試作で確認する必要がある（6 章）。

## 2. C1 で満たしたい要件

| # | 要件 | 現行の方式（公開台帳）では |
|---|---|---|
| R1 | 残高・送金額を一般に公開しない | ✕ 全口座の残高・金額が見える |
| R2 | 送金元・送金先を一般に公開しない（取引の関係が分からない） | ✕ 口座ID（仮名）どうしの送金が見える |
| R3 | 銀行は口座を凍結できる（送金・償還を止める。受取も止められる） | ○ |
| R4 | 銀行は所有者の鍵なしに強制移転・強制償還できる | ○ |
| R5 | 銀行（必要に応じて監督当局）は全取引・残高を把握できる | ○（誰でも把握できる） |
| R6 | 二重使用・残高の水増しができない | ○ |

トークン化預金では、**銀行はもともと全預金者の残高を知っている**。守るべきなのは「一般（他の利用者・第三者）に見えないこと」であって、「銀行からも隠すこと」ではない。この前提が、方式を選ぶうえで重要になる。

## 3. Midnight の関連機能（調査結果）

| 機能 | 分かったこと | C1 への使い道 | 出典 |
|---|---|---|---|
| 公開範囲のルール | コントラクトの公開ステートへの操作（読み書き・引数）はすべて公開される。**例外は `MerkleTree` / `HistoricMerkleTree` に入れる値**で、木の中のどれかは公開されない。秘密の値を公開ステートに書くには `disclose()` の明示が必要（コンパイラが検査する） | 秘匿したい情報は Merkle 木とコミットメントに入れる | Keeping data private / Explicit disclosure |
| `persistentCommit(value, rand)` | 乱数付きのコミットメント。入力を保護するのに十分とされ、`disclose` なしで公開できる | 「所有者・金額」を隠したまま、残高（ノート）を台帳に置く | Standard library |
| `MerkleTree` / `HistoricMerkleTree` | 葉の所属を、どの葉かを明かさずに証明できる（`merkleTreePathRoot` + `checkRoot`）。`insertIndexDefault` で葉の削除を模擬でき、`HistoricMerkleTree.resetHistory` で過去の根を無効にできる | ノートの存在証明、KYC 済み口座の所属証明、**凍結（木から外して即時に無効化）** | Ledger data types |
| `Set` + ナリファイア | 使用済みの印（ナリファイア）を `Set` に入れて二重使用を防ぐ定型 | ノートの二重使用の防止 | Keeping data private |
| Jubjub 楕円曲線（`ecMul` / `ecMulGenerator` / `ecAdd`） | 回路の中で楕円曲線の演算ができる | 「銀行の公開鍵で正しく暗号化した」ことを回路で証明する（検証可能な暗号化） | Standard library |
| ネイティブの shielded トークン（Zswap） | 金額・送金元・送金先は公開されない。発行は鍵の保有者に限定できる。コントラクトもコインを保有できる。**発行後に発行体が凍結・差押えする仕組みはドキュメントにない** | 単体では R3・R4 を満たせない | Shielded tokens |
| 選択的開示 | Midnight の設計方針として示されている。今回調べた範囲のドキュメント（標準ライブラリ・レジャーのデータ型・トークン・データの秘匿）には、コントラクトの状態に対する「閲覧鍵」のような既製の機能は見当たらなかった | 方式 C で、銀行宛ての暗号化として自前で実装する | Standard library ほか |

## 4. 方式の比較

| 方式 | 概要 | R1 金額 | R2 関係 | R3 凍結 | R4 強制 | R5 銀行の把握 | 実装の難しさ |
|---|---|---|---|---|---|---|---|
| A. 公開台帳（現行） | 残高を `Map<口座ID, 残高>` で公開管理 | ✕ | ✕ | ○ | ○ | ○ | 低 |
| B. ネイティブ shielded トークン | 預金トークンを Zswap のコインとして発行 | ○ | ○ | ✕ | ✕ | △（受取側が復号） | 低 |
| B'. B + 償還・再発行 | 問題のあるコインは使えないものとみなし、銀行が別途再発行 | ○ | ○ | ✕（コイン自体は動く） | △（実質的な差押えにならない） | △ | 中 |
| **C. ノート方式 + 発行体経路 + 銀行宛て暗号化** | 残高を秘匿ノートで持ち、KYC・凍結は秘匿の所属証明、強制措置は発行体専用の回路、ノートの中身は銀行宛てに暗号化して公開 | ○ | ○ | ○ | ○ | ○（銀行は復号できる） | **高** |
| D. 口座残高の準同型コミットメント | 口座ごとの残高をペダーセンコミットメントで持ち、楕円曲線の加算で更新 | ○ | ✕（口座ID は見える） | ○ | △（残高が分からないと引けない） | △ | 高（未検証） |

**方式 C が、要件をすべて満たせる唯一の候補**です。方式 B は秘匿性は高いものの、凍結・強制移転ができないため、預金としての統制要件（C1 の後半）を満たせません。

## 5. 方式 C の検証（PoC）

検証用のコントラクトとテストは `research/c1-private-notes/` にあります（デモとは独立）。

### 5.1 しくみ

| 要素 | 実装 |
|---|---|
| 残高 | **ノート** = (所有者の口座ID, 金額, 乱数) のコミットメント。`HistoricMerkleTree` に入れる。中身は暗号文として公開し、所有者と銀行が復号して持つ |
| 送金 | 自分のノートを 1 つ使い（Merkle 木の所属証明 + ナリファイア）、送金先へのノートとおつりのノートを作る。金額の保存（入力 = 出力）を回路で検査 |
| KYC | 「口座の葉」= (口座ID, 暗号化用公開鍵, 乱数) のコミットメントを「口座の Merkle 木」に入れる。送金元・送金先が木の一員であることを、どの口座かを明かさずに証明。口座ID だけでは葉を作れないので、登録済みかどうかを推測されない |
| 凍結 | 口座の葉を削除（`insertIndexDefault`）し、過去の根を無効化（`resetHistory`）。以後、その口座は送金元にも送金先にもなれず、発行も受けられない |
| 強制移転・強制償還 | 発行体の鍵の証明だけで実行できる回路（所有者の鍵は不要）。ナリファイアをノートの乱数とコミットメントから作るので、所有者も発行体も同じナリファイアになり、二重使用にならない。銀行はノートの中身を暗号文から復号して使う |
| 銀行による把握 | 新しいノートを作るすべての回路（発行・送金・強制移転）で、ノートの中身を銀行の公開鍵で暗号化して公開し、「正しく暗号化した」ことを回路で証明する（Jubjub の ECDH + ハッシュによるマスク）。銀行は秘密鍵で全ノートを復号し、口座ごとの残高を把握できる |
| ノートの受け渡し | 同じ暗号文を、ノートの所有者（受取人）の公開鍵宛てにも作る。受取人の公開鍵は口座の葉に含まれるので、送金元がすり替えられない。受取人は暗号文を試しに復号し、コミットメントと一致したものを自分のノートとして受け取る（おつりも同じ方法で復元できる） |
| 受取用アドレス | 送金先は、自分の口座ID・暗号化用公開鍵・葉の乱数（`Member`）を送金元に渡す。送金元はこれで「送金先が KYC 済み・凍結されていない」ことを証明する |

暗号文（ノート 1 つにつき 1 組、`ciphers` に公開）:

| 項目 | 内容 |
|---|---|
| 一時公開鍵 R | R = e × G（e はノートごとの一時秘密鍵。所有者宛て・銀行宛てで共通） |
| 所有者宛て / 銀行宛て | c_i = 平文_i + H(S.x, S.y, i)、S = e × 宛先の公開鍵。平文は [所有者の印, 金額, 乱数]（所有者の印 = 口座ID を Field に縮約した値） |
| 復号 | 平文_i = c_i − H((s × R).x, (s × R).y, i)。s は宛先の秘密鍵 |

### 5.2 確認できたこと（シミュレータ）

| # | 確認内容 | 結果 |
|---|---|---|
| 1 | 送金の公開部分（public transcript）に、送金元・送金先の口座ID、乱数、金額が含まれない | ○ |
| 2 | 同じノートを二度使えない | ○ |
| 3 | 他人のノートは使えない。金額の水増し（出力 > 入力）はできない | ○ |
| 4 | 凍結した口座は、送金・償還ができず、送金先にもなれない | ○ |
| 5 | 銀行は所有者の鍵なしで強制移転・強制償還できる（凍結中の口座のノートも）。強制移転したノートは元の所有者も使えない。銀行は対象のノートを暗号文から復号して知る（オフチェーンでの共有なし） | ○ |
| 6 | 銀行以外は強制移転・発行・凍結・口座登録ができない | ○ |
| 7 | 暗号化: 公開されるのは暗号文だけで、受取人は自分宛てのノートを、銀行は全ノートを復号できる。第三者の鍵では復号できず、銀行の鍵で受取人宛ての暗号文も開けられない。銀行は口座ごとの残高を復元できる | ○ |
| 8 | コンパイラの公開範囲の検査（`disclose`）を通る。明示的に公開しているのは、ナリファイア・コミットメント・Merkle 木の根・暗号文（公開が目的のもの）と、発行・償還の金額だけ | ○ |
| 9 | 口座の葉はコミットメントで、公開ステートに口座ID が出ない。乱数を知らなければ、口座ID から葉を作れない | ○ |
| 10 | 受取人の暗号化用公開鍵をすり替えた送金（第三者に復号させる送金）はできない | ○ |
| 11 | 乱数を使い回しても、使用済みのノートと同じナリファイアのノートは作れない（受取人に「使えないノート」を送り付けられない）。同じコミットメントのノートも作れない | ○ |
| 12 | ZK 鍵込みでコンパイルできる（全 7 回路） | ○ |

確認方法: #1〜#11 は `poc-check.ts`（シミュレータ）、#12 は `compact compile`（ZK 鍵込み）で確認しました。

公開される情報の確認結果（送金 1 回あたり）:

| データ | 内容 | チェーンに載るか |
|---|---|---|
| public transcript | ナリファイア、新しいノートのコミットメント（2 つ）とその暗号文（一時公開鍵と、所有者宛て・銀行宛ての各 3 要素）、Merkle 木の根の検査、呼んだ回路の名前（`transfer`） | **載る** |
| 回路の引数・ウィットネスの結果 | ノートの中身（口座ID・金額・乱数）、口座（口座ID・公開鍵・葉の乱数）、Merkle 木のパス、暗号化の一時秘密鍵 | 載らない（証明の生成に手元でだけ使う） |

### 5.3 証明の回路の大きさ（ZK 鍵込みでコンパイル）

証明鍵（`keys/*.prover`）の大きさです。

| 回路 | 現行（公開台帳） | 方式 C（暗号化なし、11-10） | 方式 C（暗号化あり、11-12） |
|---|---|---|---|
| 口座登録・凍結 | 約 11MB | 約 11MB | 約 11MB |
| 強制償還 | 約 11MB | 約 22MB | 約 45MB（4 倍） |
| 発行・償還 | 約 11MB | 約 22MB | 約 49MB（4.5 倍） |
| **送金・強制移転** | 約 11MB | 約 45MB | **約 99MB（9 倍）** |

- 回路の大きさは 2 のべき乗の段階で決まるので、少し大きくなるだけで次の段階（2 倍）に上がる。今回は、暗号化（楕円曲線のスカラー倍が、出力ノート 1 つにつき 3 回）、口座の葉のコミットメント、ナリファイアへのコミットメントの追加で、各回路が 1 段階上がった。
- 送金・強制移転は、ZK のパラメータ（SRS）として `bls_midnight_2p16` 以上が必要になる。現行のデモで使う `2p13`〜`2p15` に加えて、初回のコンパイルでダウンロードされる（社内のプロキシの環境では WSL から取得できないことがあるため、Windows 側で取得して `~/.cache/midnight/zk-params/` に置く）。
- 証明の生成時間も、おおむね回路の大きさに比例して長くなる見込みです（未計測）。
- 縮小の余地: 送金の 2 つの出力ノートで一時秘密鍵を共通にし、マスクの計算に出力の番号を入れれば、スカラー倍を 6 回から 4 回に減らせる。発行・償還額を公開する回路では、銀行宛ての暗号化を省ける可能性がある。

## 6. 残る課題・未検証の点

| 項目 | 内容 | 対応の方向性 |
|---|---|---|
| ~~ノートの受け渡し~~ | （11-12 対応済み）受取人の公開鍵宛てに暗号化して公開する方式を組み込んだ（5.1） | — |
| ~~銀行宛て暗号化の組み込み~~ | （11-12 対応済み）発行・送金・強制移転の回路に組み込み、回路の大きさを再計測した（5.3） | — |
| ~~口座の葉の推測~~ | （11-12 対応済み）葉を「口座ID + 暗号化用公開鍵 + 乱数」のコミットメントにした | — |
| 受取用アドレスの扱い | 送金先は、口座ID・公開鍵・葉の乱数を送金元に渡す必要がある。これを知った人は、その口座の葉を特定でき、凍結されたかどうか（葉が木から消えたか）を確かめられる | 受取用アドレスは取引相手にだけ渡す。口座ごとに複数の葉（アドレス）を登録できるようにする |
| 受取人の探索 | 受取人は、全ノートの暗号文を試しに復号して自分宛てを探す（ノートの数に比例） | 銀行が受取人に通知する。探索用の短いタグを暗号文に加える |
| 暗号文の作成者 | 暗号文の正しさは回路で保証されるが、復号した結果は、コミットメントと一致することを確かめてから使う必要がある（PoC のウォレット・銀行の処理で実施） | 本番のウォレットでも同じ確認を必須にする |
| 銀行の鍵の管理 | 暗号化用の公開鍵はデプロイ時に固定。秘密鍵が漏れると、すべてのノートの中身が分かる。鍵を替えるしくみもない | 鍵の交換用の回路、HSM での保管、監督当局宛ての鍵の追加（7 章のステップ 3） |
| メタデータ | 呼んだ回路の名前（送金・強制移転など）、時刻、件数、発行・償還の金額（PoC では発行残高の管理のため公開）は見える | 発行・償還額も秘匿するかを業務で判断する。回路をまとめて種類を見分けにくくする |
| 凍結時の副作用 | 凍結で過去の根を無効にすると、その時点で作成中の他の利用者の送金も作り直しになる | 凍結の頻度とのトレードオフ。凍結をまとめて行う |
| 同時実行（C2） | ノートとナリファイアの方式は、共有カウンタを更新しないので競合が減る可能性がある | 実ネットワークでの負荷試験で確認する |
| 証明の性能（M4） | 証明鍵が最大で約 99MB（現行の 9 倍）。ブラウザでの証明は重くなり、鍵のダウンロードも大きくなる | サーバー側での証明、回路の最適化 |
| 鍵の紛失 | ノートの中身を失うと、所有者は残高を使えない | 銀行宛ての暗号化があれば、銀行が中身を復元して強制移転で救済できる（むしろ現行より救済しやすい） |
| 発行体の強い権限（C3） | 強制移転・凍結は、発行体の鍵 1 本で実行できる | マルチシグ・承認の証明を回路に組み込む（C3 の対策と合わせる） |
| 実ネットワークでの確認 | シミュレータでのみ確認した。Preview へのデプロイ、ウォレット経由の実行、証明時間は未確認 | 次の段階の試作で確認する |
| 法務の確認 | 「銀行・監督当局には見え、一般には見えない」が守秘義務の要件を満たすかは、法務の判断が必要 | メタデータが見えることも含めて、法務・コンプライアンスと合意する |
